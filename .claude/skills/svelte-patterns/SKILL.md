# Svelte/SvelteKit

1.  **Reactivity:** Prefer Svelte 5 runes (`$state`, `$derived`, `$effect`) over legacy store syntax where possible.
2.  **Data Fetching:**
    - Do not use `+page.server.ts` for data loading if the app is purely SPA/static.
    - Fetch data client-side using the typed API client wrappers in each web app's `src/lib/clients.ts`.
3.  **Components:** Keep domain/business rules and reusable logic outside of `.svelte` files. Component-local UI state, handlers, form wiring, and query/mutation declarations may live in `.svelte` when they are page/component-specific; move reusable or complex logic to `.ts` support files.
4.  **Imports:** Group imports with installed package dependencies first, then external/local file references second. Sort import statements alphabetically by module specifier within each group.

## Naming and Organization

- Use `PascalCase.svelte` for Svelte component files, such as `UserProfile.svelte`.
- Use `PascalCase` for component names in imports, such as `import UserProfile from ...`.
- Keep SvelteKit route files as framework-defined names, such as `+page.svelte`, `+layout.svelte`, and `+error.svelte`.
- Use `kebab-case` for route directories, such as `sign-in`.
- Use `camelCase` for utility and non-component modules.
- Put shared web app reusable components under meaningful folders in `apps/web-*/src/lib/components/`, such as `sidebar`, `modal`, `loader`, and `upload`.
- Put module-specific web app components under `apps/web-*/src/lib/modules/<module>/components/`, such as `modules/auth/components/SignInForm.svelte`.
- Keep module support files under kind-based subdirectories such as `utilities`, `state`, and `queries` when those files are specific to one module.
- Do not use a generic `components/default` folder.
- shadcn-svelte components in `packages/ui/src/components/` follow the naming conventions generated by the `shadcn-svelte` CLI.

## Route Files

- Keep `+page.svelte`, `+layout.svelte`, and `+error.svelte` thin; they are route composition files.
- Route files may contain route-specific imports, simple page/layout composition, minimal route wiring, and tiny static placeholders while scaffolding.
- Do not put substantial page workflows, forms, TanStack queries or mutations, reusable UI blocks, complex state/effects/handlers, or domain logic directly in route files.
- Put shared reusable web UI under `apps/web-*/src/lib/components/`.
- Put feature/module-specific page components under `apps/web-*/src/lib/modules/<module>/components/`.
- Put reusable or complex support logic under module-specific folders such as `utilities`, `state`, and `queries`.
- Prefer route files that compose named components:

```svelte
<script lang="ts">
    import SignInPage from '$lib/modules/auth/components/SignInPage.svelte'
</script>

<SignInPage />
```

- For full pages, use page-level component names such as `DashboardPage.svelte`, `SignInPage.svelte`, or `MemberDashboardPage.svelte`.

## Script Organization

- For custom web app components under `apps/web-*`, organize multi-concern `<script lang="ts">` blocks with fixed-order, double-digit boxed banners.
- Omit empty sections without renumbering. For example, a component may jump from `01. Properties` to `03. State` when it has no constants.
- Keep generated or shadcn-style primitives under `packages/ui` flexible unless they become complex enough to benefit from the same structure.
- Imports stay first, grouped and alphabetized by module specifier.
- Use these section banners exactly:

```typescript
////////////////////
// 01. Properties //
////////////////////

///////////////////
// 02. Constants //
///////////////////

///////////////
// 03. State //
///////////////

/////////////////
// 04. Derived //
/////////////////

/////////////////
// 05. Queries //
/////////////////

///////////////////
// 06. Mutations //
///////////////////

///////////////
// 07. Forms //
///////////////

/////////////////
// 08. Effects //
/////////////////

//////////////////
// 09. Handlers //
//////////////////

/////////////////
// 10. Helpers //
/////////////////
```

- `01. Properties`: `$props()` destructuring and `$bindable` props.
- `02. Constants`: immutable config, menus, maps, schema aliases, and static display data.
- `03. State`: `$state(...)` declarations and plain mutable `let` values.
- `04. Derived`: `$derived(...)` declarations.
- `05. Queries`: TanStack `createQuery(...)` declarations.
- `06. Mutations`: TanStack `createMutation(...)` declarations.
- `07. Forms`: form setup, form field aliases, and form subscriptions.
- `08. Effects`: `$effect(...)` blocks and lifecycle-style side effects.
- `09. Handlers`: submit handlers, UI events, and user-triggered actions.
- `10. Helpers`: lower-level formatting, parsing, validation, and implementation helpers.
- Do not use a broad `Initialization` section; initialize values in the section that describes what they are.
- Values initialized or updated by `$effect` belong in `03. State` first, then are populated in `08. Effects`.

## Function Style

- Prefer named `function` declarations for local handlers, helpers, validators, callbacks, and event logic when allowed.
- Keep arrows for library APIs and inline adapters, including `createQuery(() => ...)`, `createMutation(() => ...)`, `createForm(() => ...)`, snippets, and short template callbacks.
- Use hoisted functions so query, mutation, form, and state declarations can stay in their ordered sections.
- Move reusable or complex logic into `.ts` utilities instead of growing `.svelte` scripts.

## TanStack Query

- Use `createQuery(() => ({ queryKey, queryFn }))` and `createMutation(() => ({ mutationKey, mutationFn }))` with typed Hono clients from `src/lib/clients.ts`.
- Do not typecast `await response.json()` results from Hono typed clients. Destructure `{ data, error, success }`, throw `new Error(error.message)` when `success` is false, then return `data`.
- Exception: endpoints that intentionally return no data/body, such as `204 No Content` heartbeat or liveness checks, may return the typed client response directly from the query function. Do not force those endpoints into the `TApiResponse` JSON envelope just to satisfy this pattern.
- `TApiResponse` branches intentionally expose the inactive side as `null` (`error?: null` on success, `data?: null` on error) to support this destructuring pattern.
- Keep query and mutation keys stable arrays. Add dynamic values to mutation keys as needed, such as record IDs or action variants.

```typescript
const resourceQuery = createQuery(() => ({
    queryKey: ['resource'],
    queryFn: async () => {
        const response = await honoClient.resource.read.$get()
        const { data, error, success } = await response.json()
        if (!success) throw new Error(error.message)
        return data
    },
}))

const updateResourceMutation = createMutation(() => ({
    mutationKey: ['resource', 'update', resourceId],
    mutationFn: async (payload) => {
        const response = await honoClient.resource.update.$post({
            json: payload,
        })
        const { data, error, success } = await response.json()
        if (!success) throw new Error(error.message)
        return data
    },
}))
```

## Fonts

- Load web fonts from each SvelteKit app's `static/fonts/` directory and reference them with root-relative URLs such as `/fonts/inter-variable.woff2`.
- Prefer `.woff2` over `.woff` whenever available.
- If a required font is not already available in `static/fonts/`, download it only from a trusted, reputable source such as the font foundry, Google Fonts, or the official project repository, then commit the font asset and matching `@font-face` CSS.

# UI Component Library (`packages/ui`)

- **Built with:** `@sveltejs/package` (`svelte-package`).
- **Components:** shadcn-svelte (backed by bits-ui). See `packages/ui/src/components/` for the full list.
- **Config:** `components.json` at `packages/ui/` root defines aliases and paths.
- **Utility:** `@PROJECT_NAME/ui/utils` exports the `cn()` helper (`clsx` + `tailwind-merge`).
- **Styling:** Tailwind CSS v4 via `@tailwindcss/vite`, with theme CSS (zinc, oklch) and `tw-animate-css` in `src/styles/globals.css`. Import shared styles via `@PROJECT_NAME/ui/styles`.
- **Icons:** `@lucide/svelte`.
- **Note:** `tsconfig.json` intentionally does not extend `tsconfig.base.json` — it uses `bundler` module resolution required by Svelte tooling, which conflicts with the root config's `nodenext` resolution.
