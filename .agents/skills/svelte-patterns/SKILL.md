# Svelte and SvelteKit

## Core Rules

- Prefer Svelte 5 runes (`$state`, `$derived`, `$effect`) over legacy stores where practical.
- This project is SPA/static. Do not use `+page.server.ts` for data loading; fetch client-side through each app's typed `src/lib/clients.ts` wrappers.
- Keep reusable or complex domain logic outside `.svelte` files. Component-specific UI state, handlers, forms, queries, and mutations may stay local.
- Group installed package imports before external/local imports and alphabetize module specifiers within each group.

## Naming and Placement

- Name components and their files with `PascalCase`, such as `UserProfile.svelte`.
- Keep framework route filenames (`+page.svelte`, `+layout.svelte`, `+error.svelte`) and use kebab-case route directories such as `sign-in`.
- Use camelCase for utility and other non-component modules.
- Put app-wide reusable components in meaningful folders under `apps/web-*/src/lib/components/`, such as `sidebar`, `modal`, `loader`, and `upload`; never use `components/default`.
- Put feature components in `apps/web-*/src/lib/modules/<module>/components/`.
- Put feature support code in kind-based folders such as `utilities`, `state`, and `queries`.
- Leave `packages/ui/src/components/` primitives in the naming and structure generated by `shadcn-svelte`.

## Route Files

- Keep route files thin: route-specific imports, simple composition, minimal wiring, and small static scaffolding only.
- Move workflows, forms, TanStack queries/mutations, reusable UI blocks, complex state/effects/handlers, and domain logic into app-wide or feature components and support files.
- Compose full pages from named page components such as `DashboardPage.svelte`, `SignInPage.svelte`, or `MemberDashboardPage.svelte`:

```svelte
<script lang="ts">
    import SignInPage from '$lib/modules/auth/components/SignInPage.svelte'
</script>

<SignInPage />
```

## Script Organization

For multi-concern custom components under `apps/web-*`:

- Keep imports first.
- Use the exact fixed-order, double-digit banners below.
- Omit empty sections without renumbering.
- Keep generated and shadcn-style `packages/ui` primitives flexible unless their complexity warrants this structure.

```typescript
////////////////////
// 01. Properties //
////////////////////

///////////////////
// 02. Constants //
///////////////////

///////////////
// 03. State //
///////////////

/////////////////
// 04. Derived //
/////////////////

/////////////////
// 05. Queries //
/////////////////

///////////////////
// 06. Mutations //
///////////////////

///////////////
// 07. Forms //
///////////////

/////////////////
// 08. Effects //
/////////////////

//////////////////
// 09. Handlers //
//////////////////

/////////////////
// 10. Helpers //
/////////////////
```

Section ownership:

1. `Properties`: `$props()` destructuring and `$bindable` props.
2. `Constants`: immutable config, menus, maps, schema aliases, and static display data.
3. `State`: `$state(...)` and mutable `let` values, including values later populated by effects.
4. `Derived`: `$derived(...)`.
5. `Queries`: TanStack `createQuery(...)`.
6. `Mutations`: TanStack `createMutation(...)`.
7. `Forms`: form setup, field aliases, and subscriptions.
8. `Effects`: `$effect(...)` and lifecycle-style side effects.
9. `Handlers`: submit handlers, UI events, and user actions.
10. `Helpers`: lower-level formatting, parsing, validation, and implementation helpers.

Do not create a broad `Initialization` section; initialize values in the section describing what they are.

## Function Style

- Prefer named `function` declarations for local handlers, helpers, validators, callbacks, and event logic when the API permits.
- Keep arrows for APIs and inline adapters such as `createQuery(() => ...)`, `createMutation(() => ...)`, `createForm(() => ...)`, snippets, and short template callbacks.
- Use function hoisting to keep query, mutation, form, and state declarations in their required sections.
- Move reusable or complex functions to `.ts` utilities.

## TanStack Query

- Use `createQuery(() => ({ queryKey, queryFn }))` and `createMutation(() => ({ mutationKey, mutationFn }))` with typed Hono clients.
- Never typecast `await response.json()` from a typed Hono client.
- Preserve `responseJson` until checking its `success` discriminant. Prefer an early failure guard, then access success-only data and pagination fields.
- Handle both branches explicitly only when failure is meaningful and non-terminal.
- For failures needing metadata, read `code`, `message`, and `requestId` from `responseJson.error` after narrowing.
- For no-body liveness endpoints, throw unless `response.ok` and return the typed response directly. Shared `ky` does not throw for HTTP errors; network and DNS failures reject naturally. Do not add a `TApiResponse` envelope.
- Keep query and mutation keys as stable arrays. Include dynamic identifiers or action variants where relevant.

Canonical response handling:

```typescript
const resourceQuery = createQuery(() => ({
    queryKey: ['resource'],
    queryFn: async () => {
        const response = await honoClient.resource.read.$get()
        const responseJson = await response.json()

        if (!responseJson.success) {
            throw new Error(responseJson.error.message)
        }

        return responseJson.data
    },
}))
```

For paginated success, destructure `{ data, count, limit, offset }` only after the guard. Mutations follow the same narrowing pattern; omit the return when no response data is useful.

### Debounced Search

- Never bind an input directly to state used by `queryKey` or `queryFn`; every keystroke would bypass the debounce.
- Initialize separate draft and applied values from a plain `initialSearchFilter`.
- Bind the input to `inputSearchFilter`; use `searchFilter` in the query and URL.
- Do not initialize draft state with `$state(searchFilter)` because it captures another rune's initial value and causes warnings.
- When syncing URL parameters, update both states. When applying input, debounce copying the draft into applied query/URL state.
- Lookup/autocomplete may use a shorter delay or separate `debouncedSearchTerm`, but query keys must use the applied/debounced value.

```svelte
<script lang="ts">
    const initialSearchFilter = page.url.searchParams.get('searchFilter') || ''

    let searchFilter = $state(initialSearchFilter)
    let inputSearchFilter = $state(initialSearchFilter)

    const listQuery = createQuery(() => ({
        queryKey: ['items', searchFilter],
        queryFn: () => client.items.$get({ query: { searchFilter } }),
    }))

    const handleSearchInput = debounce(() => {
        applySearch(inputSearchFilter)
    })

    function syncFromUrl(url: URL) {
        searchFilter = url.searchParams.get('searchFilter') || ''
        inputSearchFilter = searchFilter
    }
</script>

<input bind:value={inputSearchFilter} oninput={handleSearchInput} />
```

## Submission Safety

- Add a component-local lock such as `isSubmitting`, `isSaving`, or `isConfirming` to non-idempotent create/update/remove flows even when mutation pending state exists.
- Begin guarded handlers with an early return, set the lock before awaiting, and release it in `finally`.
- Prefer `mutateAsync` so success, failure, and cleanup stay in one `try/catch/finally`.
- Disable submit, confirm, cancel, abort, back, and close controls while the local lock or relevant mutation is pending.
- Never show or enter success UI from an error callback.
- If persistence succeeds but a UI follow-up fails, show a saved-record warning rather than encouraging a duplicate retry.
- Clear or reset completed create state immediately after confirmed persistence when leaving it visible could permit resubmission.
- For several actions behind one modal, use one shared action lock and include it in every action's disabled state.

### Idempotent Create Attempts

- Generate UUID v7 once per create attempt and include it in the payload when the endpoint requires `idempotencyKey`.
- Preserve the key across all failed retries, including network failures where persistence may have succeeded.
- Rotate the key only after confirmed persistence and local cleanup.
- Preserve attempt-coupled snapshots, such as receipt or print data, until creation is confirmed.

## Fonts

- Store fonts in each app's `static/fonts/` and reference them with root-relative URLs such as `/fonts/inter-variable.woff2`.
- Prefer `.woff2`.
- If a font is missing, download it only from a trusted foundry, Google Fonts, or the official project repository; commit the asset and matching `@font-face` CSS.

## Shared UI (`packages/ui`)

- Build with `@sveltejs/package` (`svelte-package`).
- Use shadcn-svelte components backed by bits-ui from `packages/ui/src/components/`.
- Keep aliases and paths in `packages/ui/components.json`.
- Import `cn()` from `@PROJECT_NAME/ui/utils`; it combines `clsx` and `tailwind-merge`.
- Import shared Tailwind v4 theme styles from `@PROJECT_NAME/ui/styles`; their source is `packages/ui/src/styles/globals.css` and uses `@tailwindcss/vite`, zinc/oklch theme CSS, and `tw-animate-css`.
- Deep-import Lucide icons from `@lucide/svelte/icons/*`, not the barrel, and suffix names with `Icon`: `import SearchIcon from '@lucide/svelte/icons/search'`.
- Do not make `packages/ui/tsconfig.json` extend the root config. It requires bundler resolution for Svelte tooling, while the root uses `nodenext`.
